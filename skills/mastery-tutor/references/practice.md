# Practice: using ideas nobody named

One session per phase, before the checkpoint. No new material.

## Purpose
A check right after a lesson tells you whether the learner understood something they just heard. Real work is harder: nobody says which idea applies, and the learner has to notice it from the problem. Practice rehearses that noticing.

## Choosing targets
Start from the review queue (`review.md`): everything due, lowest predicted recall first, plus anything taught but never checked. If the queue is short, add ideas that many later modules depend on.

## Problem types
- **Use it:** a short problem in an unfamiliar setting that quietly needs one idea.
- **Choose it:** two setups that differ in one detail, where that detail decides which idea applies.
- **Chain it:** a bigger problem that needs several ideas in sequence.

Move a target from Use to Choose to Chain as it succeeds. If it fails at a later type, go back a type.

## Building a problem
- If `sources/` holds a past exam, copy its format: the same task types, wording, marking and length. The learner should meet nothing new in the real exam except the content.
- Solve it yourself and write the solution in the session log before showing it.
- Look for a way around the target idea. If there is one, the problem trains the shortcut instead; change it.
- Don't mention the target idea in the wording.
- Rotate targets; never two problems on the same idea back to back.
- Tune difficulty so most problems are solved, with some effort. Solved easily: harder next time. Solved with help: same level. Not solved: easier.

## Helping when stuck
Three levels, one per request:
1. **Nudge:** point at the part of the problem that matters.
2. **Narrow:** say which group of ideas to look in, or name the idea.
3. **Show:** walk through the next move.

Aim help at the earliest point where their reasoning went off, even if they feel stuck later. Clarifying badly worded problems doesn't count as help. Record the level used; it's the real difficulty of the problem. Log each problem in the review log against every idea it needed: needing Narrow or Show counts as Hard, a miss as Again.

## Responding to answers
- **Wrong:** say so and point to where it first goes off, without the fix. Let them try again.
- **Right:** confirm and name the key move in one line.
- Note why a miss happened: *didn't think of it*, *picked the wrong idea*, *right idea, botched it*, or *the idea itself is wrong* (a misconception: nudge, don't lecture).
- A problem ends when it's solved or the learner calls it. Either way, finish by showing the full solution, and on a stop, which idea it needed. Wait for them before posing the next one.

## Shape of the session
Start with a couple of easy problems to get the topic moving, mix targets and types through the middle, and finish by re-testing every miss and every problem that needed Narrow or Show, each in a new setting.
